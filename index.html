01 — The Mindset

The rule that just broke

For twenty years software ran on one promise: same input, same output. Press the button, get the answer. Every time. An LLM quietly tears that promise up. Same prompt, three different replies — and that's not a bug. It's the entire point.

Classic code · Deterministic

add(2, 3)

A function maps inputs to one fixed output. Run it a million times — identical result. This is the world you already know.

> add(2,3) → 5
> add(2,3) → 5
> add(2,3) → 5
An LLM · Probabilistic

name_my_cafe()

Same prompt, sampled fresh each time from a cloud of likely answers. You're not calling a function — you're rolling a very well-educated dice.

> "name my chai café" → "Chai Theory"
> "name my chai café" → "DeskBrew"
> "name my chai café" → "The Steam Room"

You're no longer writing instructions. You're shaping the odds of what comes out.

— the whole job, in one sentence

02 — What it actually is

It's a function. Strip the magic.

Here's the whole thing in one line: an LLM takes some text and predicts the single most likely next chunk of text. Then it sticks that on the end and does it again. And again. Tokens, embeddings, transformers, attention — every fancy word you'll hear today is just plumbing to make that one guess better.

03 — Tokens

The model can't see words

Small confession that explains a hundred weird behaviours: the model never sees words. It sees tokens — sub-word fragments. "unbelievable" might become un · believ · able. And here's the kicker — you're billed per token, not per word.

consequence i

Your bill

APIs charge per token. Every extra word in a prompt is real money at scale. Tighter prompts = cheaper systems.

consequence ii

The language tax

Hindi, Tamil, Telugu can use 3–5× more tokens than the same sentence in English. Same meaning, more cost, slower replies.

consequence iii

Counting is shaky

Palindromes, exact find-and-replace, letter counts — anything character-level is fragile, because tokens hide the characters.

04 — Embeddings

Meaning, stored as coordinates

Computers don't understand "king" — they understand numbers. So every token becomes a long list of numbers: an embedding. The beautiful part: they're arranged in space so similar meanings sit close together, and relationships become directions you can do arithmetic on.

The famous one: King − Man + Woman

Nobody programmed "royal" or "gender" into the model. It discovered those directions on its own, just from reading.

05 — Attention

How words look at each other

This is the 2017 idea that changed everything (the paper was literally called "Attention Is All You Need"). Before producing each word, every token gets to look at every other token and decide which ones matter. That's how the model handles context — and resolves sentences that should be impossible.

The pronoun puzzle

live

Flip one word and watch what "it" points to change. Same sentence structure — opposite meaning. Attention is what figures this out.

The trophy didn't fit in the suitcase because it was too big.

🔍 Attention room

Who matters right now?

Every token looks across the whole sentence and weights what's relevant. "it" leans hard on "trophy" or "suitcase" depending on context.

🧠 Feed-forward room

Think, then pass up

After attention gathers context, each token gets processed and handed to the next layer. Stack ~50 of these and you get GPT-scale reasoning.

◆ Encoder = the listener

It understands the input

Like a person reading your whole sentence before replying — taking in every word and how they relate, building a rich picture of meaning. Great for understanding tasks: search, classification, sentiment.

decoder = the speaker ◆

It produces the output

Like a person speaking one word at a time, each choice shaped by what they've already said. Great for generation: chat, writing, translation. GPT is basically a giant decoder.

Encoder reads the room. Decoder speaks the words. Stack dozens of each, and you get every chatbot you've ever used.

Three ways to wire it up

You don't always need both halves. Pick the parts that fit the job — and you get three different families of model.

EEE

The reader 📖

All understanding, no writing. Reads the whole input at once and outputs a label or a score — not new sentences.

Good for: search, spam detection, sentiment, "is this review positive?"

Pure generation. Reads what's there and keeps adding the next word, forever. No separate "understanding" stage needed.

GPT · Gemini · Claude · Llama

The translator 🔄

Read one thing fully, then write a different thing. The original 2017 design — a clean input→output mapping.

Good for: translation, summarisation — where input and output differ.

T5 · original Transformer

So why is ChatGPT decoder-only?

Because chat is just one long autocomplete.

An encoder is built to read a fixed input and stop. But a conversation never stops — every reply becomes part of the input for the next reply. So you don't want a separate "reader" and "writer"; you want one thing that reads everything so far and writes the next bit. That's exactly a decoder.

1Your whole chat — system prompt, history, your new question — is one big block of text.
2The decoder reads all of it and predicts the next word of the reply.
3It adds that word, then reads everything again (including the word it just wrote) and predicts the next.
4Repeat until it decides to stop. The "masked" attention guarantees it only ever uses the past — so it can generate endlessly.
An encoder finishes reading and gives a verdict. A decoder never has to stop talking — which is exactly what a chatbot needs.

07 — Training

How it actually learned

A model isn't built once — it's raised in three stages. Each stage gives it something different: knowledge, then behaviour, then values. Click through them.

1

Pre-training → raw knowledge

Read a huge chunk of the internet, predicting the next token billions of times. Slow, expensive, done once. This is where it learns facts, grammar, code, and the shape of the world.

2

Fine-tuning → good behaviour

Show it curated examples of helpful answers in the right format. Cheaper, repeatable. This turns a raw text-predictor into something that acts like an assistant.

3

RLHF → human values

Humans rank answers; the model learns to prefer the ones people actually like — helpful, honest, harmless. This is the polish that makes it usable by everyone.

Engineer's note: fine-tuning is great for style and format. For facts that change, don't fine-tune — use retrieval (we'll get there). Baking facts into weights is how you build a model that's confidently out of date.

09 — Limits & hallucination

Why it lies with a straight face

A model never says "I don't know" unless it's been taught to. Its only instinct is to produce the most plausible next token — and a confident wrong answer is often more plausible-sounding than the truth. Hallucination isn't a malfunction. It's the same machinery, applied where it has no real knowledge.

why it happens

It's optimised for plausible, not true

Training rewards text that looks right. When it doesn't know, it fills the gap with something statistically likely — a fake citation, a confident wrong date, an API that doesn't exist.

what to do

Engineer around it

Give it the facts in the prompt (retrieval). Ask for sources. Keep temperature low for factual tasks. Verify anything that matters. Never ship raw model output as ground truth.

11 — Thinking like an AI engineer

From toy to production

A clever prompt is a demo. A system is a product. The engineer's real job starts here: decomposing problems, knowing when not to use an LLM, and watching three numbers — cost, latency, and quality.

RAG — giving the model your facts

live

The #1 pattern in real products. Instead of hoping the model knows, you retrieve the right document and hand it over at question time. Play the pipeline.

1

User asks a question

"What's our refund policy for opened items?"

2

Search your knowledge base

Find the most relevant chunks from your own docs using embeddings.

3

Stuff them into the prompt

"Using THIS policy text, answer the question." Now the model has the facts.

4

Grounded answer

Accurate, current, citable — and you control the source of truth.

✓ reach for an LLM

Fuzzy, language-shaped work

Summarizing, drafting, classifying messy text, extracting structure from chaos, answering from documents, code assistance. Anywhere "close enough + reviewed" wins.

✕ don't reach for one

When a normal function works

Exact math, billing, anything needing a guaranteed identical answer, hard real-time, or where a wrong answer is dangerous and unreviewed. Use real code.

💰 cost

Per token, at scale

Cheap per call, terrifying per million. Trim prompts, cache, and pick the smallest model that passes your evals — not the biggest available.

⚡ latency

It generates serially

One token at a time. Long outputs feel slow. Stream responses, keep outputs tight, and don't call a giant model when a small one clears the bar.

✅ quality / evals

Vibes don't scale

Build a set of 20+ input→expected pairs. Run them on every prompt change. This is unit testing for LLMs — the thing that separates a hobby from a product.
